# Mango: мобильные номера сотрудникам под ключ

Выполняй единый процесс: подбор → согласованный план → подписи → отдельные входящие схемы → привязки номеров → исходящий АОН → повторное чтение. Поддерживай и частичный запрос, не расширяя его до полного процесса без поручения пользователя.

## Когда применять

| Запрос | Действие |
|---|---|
| «Подбери чистые номера, пока не меняй» | Только справочник и история; не выполнять mutations |
| «Настрой номера менеджерам как раньше» | Составить весь план, проверить актуальные назначения и недостающие параметры |
| «Сделай всё вместе» с подтверждёнными получателями/переходами | Выполнить согласованные изменения одним управляемым процессом |
| «Продолжай» после сбоя | Сверить журнал и живое состояние; не повторять записи вслепую |
| «Проверь звонком / с фразой через Asterisk» | Прочитать [references/test-call.md](references/test-call.md); звонить только по прямому поручению |

## Границы

- Этот навык не даёт постоянного разрешения менять Mango. Право на запись определяется текущим поручением. «Подбор», «проверка» и «черновик» не разрешают настройку.
- Изменять только перечисленные номера/сотрудников и создавать только согласованные отдельные схемы. Общие схемы, состав групп, прочих сотрудников, тарифы, SIP-пароли, права и CRM не менять.
- Для данных «Зари» использовать также `zarya-crm-semantic-layer`; Озеро и аналитические БД только READ ONLY. Настройка выполняется в Mango, не правкой реплики.
- Не совершать тестовые звонки без отдельного поручения. Сохранённая настройка не доказывает, что получатель увидел нужный АОН.
- Секреты получать из существующего разрешённого источника, хранить только в памяти. Не помещать их в навык, журнал, исходники или вывод.

## Входные данные и план

Установи для каждой строки: ФИО, живой ID сотрудника и добавочный, выбранный номер, подпись, индивидуальную входящую схему, порядок получателей/таймауты и исходящий номер. Уточняй только существенные отсутствующие решения.

Согласованный пример из задачи (не универсальная настройка):

`СЕВЕР / МП УД / Моб / Фамилия И.О.`; персональный МП 20 секунд → конкретный резервный сотрудник 20 секунд → группа из схемы «КЦ СЕВЕР ОБЩИЙ».

Не назначай резервного сотрудника, Север, интервал 20 секунд или прежние номера новым задачам автоматически. Неоднозначного сотрудника сопоставляй по ФИО и добавочному, не по одной фамилии. Порядок номеров/ФИО явно проговори перед записью, если пользователь дал их отдельными списками.

Для детерминированной проверки JSON-плана используй [scripts/validate_plan.py](scripts/validate_plan.py). Он не подключается к Mango и ничего не меняет. Успешная проверка плана не заменяет живой preflight.

## 1. Подбор без звонков

Перед подбором прочитай [references/selection.md](references/selection.md).

- Проверяй текущий справочник и фактические звонки за точный интервал Europe/Moscow; будущий период не равен отсутствию прошлой активности.
- Считай попытки, включая неотвеченные; не ограничивайся разговорами.
- Данные ночной загрузки дополняй отчётом Mango от конца загрузки до фиксированного среза. Проверяй пропуски, пагинацию и поля исходящего номера.
- Ноль звонков не доказывает свободу номера: проверяй активную схему, подписи, назначения сотрудникам/группам и другие интеграции. При признаках чужого использования выбирай другой номер или уточняй.
- «Чистый» означает только отсутствие зарегистрированной исходящей активности в проверенном интервале, не отсутствие спам-репутации.

## 2. Preflight

Перед любой настройкой прочитай [references/mango-api.md](references/mango-api.md).

1. Проверь авторизованный продукт/аккаунт, свежие линии, сотрудников и схему резервного направления.
2. Сохрани снимок выбранных объектов и минимальную сравнительную проекцию остальных объектов без паролей/токенов.
3. Различай ID: `abonent_id` номера, `profile_id` линии, `member.id`, `default_number_id` устройства сотрудника и `schema_id` не взаимозаменяемы.
4. Подпись Mango ограничена 40 символами (подтверждено API 21.10.2026). Полное ФИО не обрезать молча; предложить инициалы, если сокращение ещё не согласовано.
5. У конечной группы получи ID из живого содержимого утверждённой общей схемы и проверь её название. Не путай ID схемы с ID группы ACD.
6. Проверь алгоритм вызова сотрудника, его номер по умолчанию и `use_cc_numbers`. Не выключай конфликтующий переключатель без понимания его эффекта и разрешения.
7. Сформируй preview: номер → сотрудник → подпись → входящие шаги → исходящий АОН. Если весь процесс уже прямо разрешён и параметры ясны, повторное подтверждение не требуется.

## 3. Выполнение

- Создай локальный журнал операции до первой записи: план, исходные ID/значения, время, этапы `pending/verified/rejected/uncertain`.
- Перед каждым шагом повторно читай объект и сравнивай с ожидаемым снимком. При чужом изменении остановись, не затирай его.
- Переименуй только выбранные номера. `number_title` может автоматически повторить новую подпись; разрешай только это проверенное производное изменение.
- Для каждого номера создай отдельную схему с уникальным именем. Проверяй, нет ли уже схемы с тем же именем и содержимым, прежде чем создавать новую.
- Проверь созданное дерево, получателей и таймауты повторным чтением; только после этого активируй схему на `profile_id` выбранного номера.
- Назначь исходящий АОН сотрудника точечным `memberUpdate` только поля `subst_ani_abonent_id`, указав `abonent_id` нового номера. Не меняй `default_number_id` и список устройств вместо АОН.
- После каждого ответа проверяй прикладной `status`, а не только HTTP 200; затем read-back. Допустим ограниченный повтор чтения при задержке, но не слепой повтор mutation.

## Сбой и повторный запуск

Таймаут или оборванный ответ после записи = неопределённый результат, не подтверждённая ошибка. Останови дальнейшие mutations, прочитай состояние и журнал. Для создания ищи новую схему по имени, разнице ID и полному дереву. Если исход установить нельзя, сообщи и не создавай вторую.

Подтверждённый отказ, например слишком длинная подпись, не равен применённому изменению. Исправляй только известную причину в рамках пользовательского решения. Не откатывай изменения автоматически, если это может затереть последующие ручные правки.

При частичном выполнении явно перечисли, какие номера уже настроены, какие этапы остались, и не объявляй весь процесс успешным.

## Итоговая проверка и ответ

- Повторно прочитай все выбранные подписи, деревья схем/таймауты, активные привязки и исходящие АОН.
- Сравни исходный/конечный снимки: нецелевые сотрудники и привязки линий неизменны, существующие общие схемы не редактировались.
- Дай компактную таблицу «полный номер — сотрудник — добавочный», общую цепочку резервирования и факт проверки конфигурации.
- Укажи ограничения истории/АОН и отсутствие проверки реальным звонком, если звонок не проводился.

Правильно: настроить исходящий номер точечным `subst_ani_abonent_id` и проверить неизменность остальных полей. Неправильно: заменить устройство сотрудника или редактировать общую схему, обслуживающую сотни других номеров.

## Проверка входящих реальным звонком

Для авторизованного теста с аудиофразой используй [references/test-call.md](references/test-call.md). Готовая запись — [assets/crmcalls-test.wav](assets/crmcalls-test.wav). Принятие команды, ответ АТС, запуск аудио и ответ конкретного сотрудника — разные уровни доказательства; в результате указывай подтверждённый уровень.
