# Mango: отбор номеров без исходящей активности

## Источники в среде «Зари» (снимок 21.10.2026)

Аналитическая ночная БД: PostgreSQL `<SERVICE_HOST>`, база `skorozvon`, схема `mango`. Это не `zarya_mango_new`. Источники: `lines`, `users`, `groups`, `calls`, `call_base_stats`, `etl_runs`. Проверяй выбранную БД/схему и актуальный состав полей. Используй существующее подключение, READ ONLY, параметризованные ограниченные SELECT и `statement_timeout`.

Ночной сборщик `/opt/mango-monitor`; сам сборщик, права, расписание и конфигурацию для анализа не менять. Учётные данные брать из разрешённого существующего подключения, не копировать в навык.

## Полнота и определения

1. Зафиксируй начало/конец среза Europe/Moscow. «Последний месяц» переведи в явные даты; не смешивай календарный месяц, 30 дней и будущий месяц.
2. В текущем справочнике отбирай российские мобильные номера после нормализации (`+7…`, `8…` → `7…`). Проверяй уникальность соответствий; не считай городские номера мобильными по имени.
3. В `calls` ранее проверенная классификация исходящих: `context_type=2`. При дрейфе схемы/семантики перепроверь. Считай все попытки, не только соединения.
4. Проверяй свежесть `etl_runs`, диапазон звонков, наличие каждого дня и полноту загрузок. Наличие хотя бы одной записи в каждом дне само по себе не доказывает полноту. При наличии контрольных количеств сверяй их. Не подменяй окончание данных временем запуска анализа.
5. Сверяй номера не только по `calls.line_number`, но и по `call_base_stats.line_number`/`from_number`. Направление базового отчёта определяй по проверенной семантике; пустой `to_extension` - прежняя эвристика возможного исходящего, не универсальный факт.
6. Учитывай записи без `line_number`; отсутствие совпадений в именованной линии не гарантирует отсутствия фактического исходящего АОН, скрытого в деталях маршрута.
7. Для кандидата проверь назначения сотрудникам/группам, текущую подпись и схему. ChatApp/MAX или чужое ФИО в подписи - повод проверить назначение, даже при нулевых звонках.

## Сегодняшний хвост через официальный VPBX API

На сервере существующий разрешённый secret-source: `/opt/mango-monitor/secrets/mango-api.env`. Не выводи его. Ключ/соль используются только в памяти.

- База: `https://app.mango-office.ru/vpbx/` (либо проверенное значение действующей настройки).
- `incominglines` - текущий справочник; сохранить безопасные поля выбранных номеров.
- `stats/request` и `stats/result` - запрос/получение отчёта, не телефонный звонок.
- Подпись: SHA256(`api_key + compact_json + api_salt`), form-urlencoded `vpbx_api_key`, `sign`, `json`.
- Для сверки кандидатов достаточны поля `entry_id,line_number,from_number,to_extension,start`; клиентские номера не сохранять и не печатать.
- Фиксированный интервал, `date_to` с учётом включительности API (в проверенном запросе конец минус 1 секунда).
- CSV `;`, UTF-8 BOM, проверка числа колонок и ограничение размера ответа. Несколько строк на один `entry_id` могут означать части звонка, не дубли: не отбрасывай их до проверки номеров.
- Не готовый отчёт кратко опрашивай с ограничением числа чтений; HTTP 404/425 ранее встречались как «ещё не готов». Не бесконечный цикл.

Веб-кабинет Mango использует отдельный `response-stats` с пагинацией. Первые 100/200 строк или один HAR не подтверждают отсутствие звонков за месяц; нужны все страницы с проверкой контрольных количеств. Полный CSV базовой статистики и полный вложенный JSON - разные уровни доказательства.

## Формулировка результата

«За [начало–конец, МСК] в проверенной истории по этим линиям/исходящим номерам зафиксировано 0 исходящих попыток; текущий справочник подтверждён [время]. Ограничения: [пробелы/пустые поля/непроверенные контрольные количества]. Это не проверка спам-меток».

Не утверждай, что номер никогда не использовался, будет свободен месяц вперёд, либо гарантированно показывается клиенту именно как проверенное поле линии.
