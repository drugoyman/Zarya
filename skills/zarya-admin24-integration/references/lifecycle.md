# Связи, события и защита от повторов

Рабочие приложения, скрипты, снимки и подключения, упомянутые ниже, задаются отдельно и не входят в публичный пакет навыка.

## Создание и авторство

Храни минимальную связь:

`portal_id, verified_author_id, local_request_id, request_key, payload_version, create_state, admin_ticket_id, admin_ticket_uuid, created_at, checked_at`.

Контактное лицо и редактируемые контакты — отдельные поля. Номер заявки, внутренний ID и UUID не взаимозаменяемы. Ссылка на заявку должна строиться по подтверждённому идентификатору и доверенному хосту; произвольный URL из webhook не пересылать без проверки.

Авторство подтверждается серверным запросом к ожидаемому порталу. Не доверяй `userId` из формы, query string, скрытому input, ФИО, почте или телефону. Для режимов без авторизации сохраняй черновик как демонстрационный/неподтверждённый, не создавай от него рабочую заявку по умолчанию.

Сверь схему актуальной формы: обязательность и типы полей, UUID услуг, допустимость длины/вложений. Если API позволяет передать внешнюю ссылку на запрос или ключ идемпотентности, сначала подтверди соответствующий контракт. Не придумывай такой параметр.

До внешнего POST запиши `creating` и полезные для сверки идентификаторы; после прикладного подтверждения сохрани ID/UUID и `created`. При обрыве оставь `unknown`, проверь возможную созданную заявку чтением. Не повторяй POST только потому, что локального `ticketId` ещё нет. Если однозначная сверка невозможна, приостанови дальнейшее создание и сообщи о неопределённости.

## Приём изменения статуса

Перед подключением webhook проверь документированный механизм подлинности и ограничения выбранного Админ24: подпись/секрет, источник, повторную доставку и доступные устойчивые event ID/версии. Если подписи нет, не выдавай случайный URL за достаточную проверку; согласуй доступный способ защиты и перечитывай заявку через доверенный API перед выводом о переходе состояния.

Храни исходный event ID или иной проверенный ключ, ID заявки, версию/время источника, предыдущий и новый статус, время получения и результат обработки. Дедупликация только по времени получения недостаточна. Для событий вне порядка не откатывай более новое состояние; сверяй текущую заявку и историю.

Выделяй переход в завершённое состояние, а не любое обновление уже закрытой заявки. «Кто закрыл» устанавливай из подтверждённого автора события/истории; текущий ответственный не обязательно закрывший сотрудник. При отсутствии доказательства укажи «сотрудник не установлен», а не подставляй ответственного.

## Уведомления

Отдельная очередь исходящих уведомлений связывает:

`ticket_id, closure_event_id_or_generation, recipient_id, sender_identity, message_kind, payload_version, state, attempt_id, server_message_id, checked_at`.

Уникальный ключ должен исключать повтор одного уведомления по одному закрытию одному получателю. Если допускается повторное закрытие после возврата, у него отдельное подтверждённое событие/поколение; один ключ только по ticket ID заблокирует нужное последующее уведомление. Политику повторного закрытия фиксируй до запуска.

Сообщение формируй из минимально необходимых данных: номер, результат, закрывший, проверенная ссылка. Личное сообщение не должно раскрывать сотруднику чужую заявку из-за сопоставления по общему телефону/почте. Отправитель определяется авторизацией действующего клиента Битрикс; текстовая подпись не меняет отправителя.

Один исполнитель забирает элемент очереди, сохраняет `sending` до запроса. После подтверждённого принятия сохраняй серверный ID; «принято» и «доставлено/прочитано» различай по реальным возможностям API. После таймаута — `unknown` и сверка истории, без слепой повторной отправки. Неопределённость нельзя автоматически исправлять сменой учётки или бота.

## Оценка и возврат

Предпочтённый сценарий — сообщение в личный чат автора, а оценка и возврат в Админ24. Это не требует автоматически создавать задачи, смарт-процессы или менять ответственных в Битрикс.

Проверь доступ по ссылке от имени целевого заявителя с нужным состоянием заявки; доступ администратора не заменяет эту проверку. UUID в URL не считай достаточной авторизацией. Не объявляй шкалу «1–5» готовой, пока не проверена фактическая шкала; в истории обсуждалась и бинарная оценка. Не нажимай оценку/возврат при диагностике: это изменяет состояние.

Для встроенных кнопок собственного обработчика потребуются проверенная сессия заявителя, проверка доступа к конкретной заявке, защита от повторов и подтверждённый API переходов. Не добавляй такую реализацию незаметно вместо согласованной ссылки Админ24. При повторном открытии проверь, остаётся ли прежняя ссылка/оценка действующей, и сообщи ограничение.

## Безопасный пилот

Пилот отдельно фиксирует тестовую заявку, автора и единственного получателя, отправителя, допустимые изменения статуса и наличие сторонних уведомлений/синхронизации. Тест «только мне» может затронуть исполнителя заявки через штатные уведомления; это нужно проверить до закрытия или возврата.

Минимальная последовательность доказательств: локальная валидация → подтверждение личности без создания заявки → разрешённое создание одной тестовой заявки и сверка связи → обработка тестового события без отправки → одна разрешённая отправка единственному адресату → разрешённая проверка оценки/возврата. Каждый этап выполняй только в порученном объёме; отсутствие разрешения на следующий не мешает завершить предыдущий локально.
