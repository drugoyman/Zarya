# Заря: аудит бизнес-процессов

Используй `zarya-crm-semantic-layer` до обращения к CRM. Озеро / sitemanager строго READ ONLY: это относится к данным, шаблонам, роботам, правам и серверным исходникам, а также UI/API. Запрос аудита или подготовки исправления не разрешает запись, запуск БП или тестовую отправку.

Для доступа сначала прочитай локальную инструкцию доступа проекта. Используй существующее разрешённое подключение без вывода секретов; недоступность исходника не обходи изменением прав или сборщика.

## Объём и получение материала

1. Определи конкретную сущность/документ, процесс и симптом: аудит конфигурации либо разбор события исполнения. Значение ТНБ и направление звонка уточняй по задаче: «клиент не отвечает» и «офис пропустил входящий» — разные события.
2. Проверь доступную БД/реплику и таблицы. Начни с метаданных известных шаблонов: ID, имя, тип документа, активность, автозапуск, изменение, длина полезной нагрузки. Снимок не считать полной производственной схемой.
3. Шаблоны и связанные процессы читай небольшими ограниченными порциями в read-only транзакции с таймаутом и rollback. Не выгружай все большие BLOB ради одного процесса. При таймауте уменьши объём; при обрезанном результате не заявляй полноту.
4. Декодируй копию как данные без выполнения PHP/активностей. Для распаковки установи предел размера, для разбора — глубины/объёма. Не используй eval, исполняющую десериализацию объектов или запуск старого скрипта с непроверенными побочными эффектами. Неподдерживаемый формат отметь явно.

Локальные ориентиры и ограничения существующего просмотрщика: [references/sources.md](references/sources.md). Просмотрщик готового снимка может не содержать всю структуру ветвлений; отсутствие блока в его проекции не доказывает отсутствие в исходном шаблоне.

## Восстановление схемы

- Составь цепочку: условия → выбор ветви → вызов вложенного БП → параметры → выбор линии → результат → конкретное действие отправки. Проверь тип документа и связи переменных/констант между шаблонами. Циклические ссылки не обходи бесконечно; фиксируй посещённые ID.
- Для каждого действия укажи ID/имя узла, тип, активность, путь от корня, условие, входные параметры и ссылки на результаты других узлов. Проверь порядок ветвей и поведение «первая совпавшая» по реальному типу активности, а не виду схемы.
- Проследи источник `license`/линии до выбранного результата. Не считай текстовую подпись линии её API ID и не смешивай обычный ChatApp, WABA, MAX и SMS в один канал.
- Проверь повторные идентификаторы состояния, повторы линий, заглушки, пустые значения, ссылки на результат другой ветви и положение выбора линии относительно времени/условий отправки. Список из нескольких линий сам по себе не доказывает ротацию, равномерность и резервирование.
- Семантику кастомной активности проверяй по её коду, если доступен разрешённый исходник. Например, совпавший `UUId` может означать общий ключ состояния только если это подтверждает реализация. Не исполняй активность для проверки гипотезы.

## Доказательства исполнения

Перед выводом используй [references/evidence.md](references/evidence.md). Для конкретного события нужны экземпляр workflow, фактический документ, время, журнал шагов, входные/выходные параметры и идентификатор сообщения провайдера в доступном покрытии. Число действий в дереве — не число отправок за запуск. Возможная ветка не доказывает, что она выполнялась; успешное действие CRM не доказывает доставку.

В отчёте дай карту процесса, подтверждённые связи, гипотезы с необходимыми проверками, покрытие и время снимка. Предложения исправлений оформляй отдельным локальным документом, без применения. Сырые шаблоны могут содержать токены, телефоны и тексты клиентов: не публикуй их и не включай в навык/общий отчёт.
