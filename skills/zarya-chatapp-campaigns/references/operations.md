# Источники и выполнение рассылок

## Проверенные локальные материалы

Проверено по коду 27.10.2026, без запуска отправок и без проверки текущего состояния API:

Найдите в разрешённом локальном проекте существующие сценарии ниже. Они не входят в публичный репозиторий; наличие навыка не делает их доступными.

| Файл | Что в нём переиспользовать после просмотра |
|---|---|
| `mailing_runner.py` | `api`, `message`, `run`: проверка состояния канала и наличия адресата, локальный журнал, запись попытки до POST, блокировка исполнителя. |
| `coupon_campaign.py` | `prepare`, `inventory`, `send`, `cycle`, `run`: подготовка списка, каталог лицензий, отправка файла с подписью, повторное чтение доступных каналов, остановка. |
| `check_campaign.py` | Проверка истории, сообщений и признака полноты; поля `historyComplete`, `nextPage`, `attemptId`, `status` — сверить их текущую семантику. |
| `mailing_scheduler.py` | Исторический способ запуска. Не запускать и не создавать новое расписание без запроса пользователя. |

Это рабочие сценарии конкретных кампаний, не универсальная библиотека. Они содержат действительные настройки, пути и составы получателей; не копируй их целиком в навык, публичный репозиторий или отчёт. Перед импортом проверь верхнеуровневые действия: импорт не должен отправлять сообщения, создавать/менять очередь либо расписание. Без такого просмотра не импортируй их даже для чтения состояния.

Частные чаты и прежние поручения не включены. Для текущей кампании проверяйте актуальное разрешение и ограничения.

## Что проверено в API-клиенте

- Используется семейство путей `/v1/licenses`, `/v1/licenses/{licenseId}/messengers/{type}/status`, проверка существования телефона и отправка сообщений по chat ID.
- Прикладные поля: `success`, `data.active`, `data.exist`, `data.chatId`, `error.code`. Лицензия и мессенджер имеют разные ID/типы; подпись линии не является ID лицензии.
- Для текста используется окончание пути `/messages/text`; для файла — `/messages/file`. Точную форму тела и текущие типы мессенджеров сверять с разрешённым клиентом/документацией, не выводить из названия интерфейса.
- Клиент различает `accepted` и ошибку, хранит отдельный tracking ID. Эти значения отражают состояние приложения, а не гарантию доставки мессенджером.
- В общем `api` есть повтор запроса после обновления токена. Перед применением к POST проверь, что исходный ответ однозначно подтверждает непринятие операции. После неизвестного исхода обновление токена не разрешает повторить отправку.

Не считай этот перечень текущим полным контрактом API. Для смены реализации сначала проверь актуальный контракт. Новые ключи, смена паролей и лицензий не входят в рассылку.

## Журнал и восстановление

Минимальная запись попытки:

`campaign_id, recipient_key, source_ref, channel, license_id, attempt_id, started_at, payload_version, state, server_message_id, checked_at, error_class`.

Полный номер нужен только в защищённом локальном источнике отправки. Для отчётов используй случайный псевдоним или HMAC с локальным секретом; обычный несолёный хеш телефона допускает перебор. Не сохраняй заголовки авторизации и необработанные тела ошибок: они могут содержать секреты и телефоны.

Рекомендуемая логика состояний:

| Состояние | Следующий шаг |
|---|---|
| `pending` | Можно отправить в пределах поручения, после проверок. |
| `sending` | Отправка начата; после сбоя считать неопределённой до сверки. |
| `accepted` | Принято API; получить серверный ID и проверить доставку отдельно. |
| `delivered` / `read` | Присваивать только при подтверждённой семантике статуса провайдера. |
| `rejected` | Подтверждённый отказ, причина известна; дальнейшее действие по правилам кампании. |
| `unknown` | Не повторять; проверить историю и разрешить неопределённость. |
| `excluded` | Причина исключения сохранена, отправки нет. |

Список отражает модель журнала, а не числовые статусы ChatApp. Для пакетного ответа проверяй каждую запись. Отсутствие сообщения на первой странице истории не доказывает, что отправки не было; пройди нужный интервал и пагинацию, учти задержку появления статусов.

Пример восстановления: до сбоя 12 попыток приняты, одна осталась `sending`, остальные `pending`. Сначала проверь неизвестную попытку. Не отправляй 12 принятых повторно и не объявляй эту одну ошибкой только потому, что процесс завершился. Пользовательская остановка сохраняется между запусками.
