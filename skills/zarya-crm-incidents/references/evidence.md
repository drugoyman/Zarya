# Как оценивать доказательства

Процедура обобщена из локальных расследований Зари; текущий инцидент проверяется заново.

| Свидетельство | Что подтверждает | Чего не подтверждает |
|---|---|---|
| Совпадающий нормализованный телефон | Связь для дальнейшей проверки | Ошибочный дубль, личность инициатора |
| Новый отдельный CONTACT_ID | Создание отдельного контакта в доступной базе | Причину создания и необходимость удаления |
| Имя автора или источник | Записанные реквизиты карточки | Кто отправил HTTP-запрос и зачем |
| Стадия «Дубль» | Текущую классификацию CRM | Алгоритм создания и правильность классификации |
| Новый лид до закрытия предыдущего | Порядок конкретных событий | Универсальное правило для всех интеграций |
| Повтор входящего ID заявки | Повтор передачи/обработки этого ID в доступных журналах | Сам по себе — сторону, начавшую повтор |
| Шаблон БП | Возможный маршрут по конфигурации | Запуск, отправку, доставку и виновника |

Проверь последовательность: исходный лид → событие закрытия → входящий запрос → ответ интеграции → новая карточка. Если запросов нет, оставь разрыв явным.

## Обезличенные примеры

- Два лида с одним телефоном, один «Офис», второй «УД»: сначала проверь допустимость пары; не объявляй дублем по одному ключу.
- В группе одного направления пять новых карточек, очередная создана до закрытия предыдущей: гипотеза «повтор создаётся только после закрытия» не объясняет всю цепочку.
- Входящий ID заявки одинаков, два ответа с разными ID лида: это основание исследовать повторную обработку и идемпотентность; обвинение отправителя без полного журнала необоснованно.
