# Источники, слои и проверки

Рабочие приложения, скрипты, снимки и подключения, упомянутые ниже, задаются отдельно и не входят в публичный пакет навыка.

Ориентиры проверены статическим чтением локальных файлов 27.10.2026. Они не подтверждают текущее развёртывание, успешность загрузки или полноту живых данных. Код сборщиков, выгрузки и подключения в навык не входят; ниже перечислены точки для чтения, не команды запуска.

## Mango

По действующему семантическому навыку ночная аналитика относится к БД `skorozvon`, схеме `mango`: `calls`, `call_base_stats`, `etl_runs`, справочники `users`, `lines`, `groups`, `trunk_numbers`. Отдельная БД `zarya_mango_new` содержит другой набор, включая `public.summary`, `calls_state`, `early_statistics`, `full_statistics`. Это датированная карта, текущую БД/схему и разрешение чтения устанавливать при подключении; не смешивать наборы по слову Mango.

Код: `mango-monitor/app/mango_etl.py`.

- `sync_calls(conn, day)` запрашивает сутки от 00:00:00 до 23:59:59, страницы по 1000 с offset, группирует по `entry_id`. Зону запроса и включённость последней секунды сверять с контрактом API и runtime; для аналитики явно задавать полуоткрытое окно.
- Повтор страницы без новых ID и короткая страница заканчивают цикл. Поэтому сам возврат функции или `status='success'` **не доказывает полноту**: повтор страницы может оборвать загрузку. Сверять total, стабильность ключей и повторное чтение; статическое наличие пагинации недостаточно.
- `mango.calls` обновляется по `entry_id`, сохраняет `raw_payload` и `synced_at`. Последняя синхронизация старой строки отличается от её `started_at`. `context_calls` внутри JSON могут содержать нужные причины, времена и длительности, отсутствующие в отдельных столбцах.
- `sync_base_stats()` загружает другой отчёт в `call_base_stats`: равенство единицы и ключей перед сравнением подтвердить отдельно. `main()` имеет scope directory/calls/base/all/parts; scope directory не доказывает свежесть звонков.
- `main()` пишет `mango.etl_runs` с scope, finished_at, status, rows_loaded; дата по умолчанию — вчера по окружению процесса. Не считать её доказанными «вчера МСК» без проверки среды. Внутренние этапы коммитятся отдельно: failed позже может сосуществовать с частично обновлёнными данными. `mango.refresh_call_parts()` — изменяющая функция, в диагностике не вызывать.

## ChatApp

Код: `chatapp-monitor/app/chatapp_etl.py`; схема: `chatapp-monitor/db/init/01_schema.sql` в том же корне.

- `persist_snapshot()` сохраняет `chatapp.lines` по `license_id`, `chatapp.line_messengers` по `(license_id, messenger_type)`, время `observed_at` UTC; историю пишет в `chatapp.line_status_history` с `run_id`. Это снимок каталога/статусов, **не история доставки сообщений**.
- `run()` фиксирует started_at/finished_at/status и line_count/messenger_count в `chatapp.etl_runs`. Ошибка одного канала записывается как `status_error`, не обязательно отменяет весь успешный снимок. Проверять ошибки и покрытие каждого канала; success не означает «все мессенджеры работают».
- Upsert обновляет встреченные записи, но сам по себе не доказывает, что оставшиеся строки входят в последний каталог. Сверять `observed_at`, состав снимка и историю, не считать все строки таблицы текущими.
- Снимок БД коммитится перед `sync_google_sheet()`. Ошибка последующей синхронизации может пометить запуск failed при уже обновлённой БД. Проверять БД и целевой лист отдельно, не публикуя данные из конфигурации или ответов.

## Скорозвон и отчётные слои

Ожидаемая папка `skorozvon-monitor` при этой проверке не найдена. Это не доказывает отсутствие сборщика на сервере. Проверенная локальная копия: `gitlab-local/skorozvon-etl/src/skorozvon_etl/`; не считать её развернутой версией автоматически.

- `pipeline.py`, `Pipeline.run()`: фиксирует end, берёт начало из `Repository.interval_start()` с overlap, листает вызовы, считает received/inserted/updated/skipped. Максимум страниц и доля невалидных записей ограничиваются конфигурацией; текущие пределы проверять, не переносить старые значения.
- `repository.py`, `interval_start()`, `start()`, `finish()`: `etl.sync_state` с pipeline_name `skorozvon_calls`, last_successful_start_at/last_successful_end_at, status, last_run_id; `etl.runs` содержит requested_start_at/requested_end_at, finished_at и счётчики. Успешный end — граница выполненного запроса, не максимальный timestamp события и не доказательство отсутствия поздних изменений.
- `Repository.calls()` использует `core.calls`, `call_fingerprint`, пакетный COPY/upsert и пропускает неизменившиеся строки. Ноль inserted не значит ноль полученных вызовов. Не выполнять этот метод или его SQL в диагностике: временная таблица, COPY, lock и upsert изменяют состояние.
- `extended.py`, `collect()`: дополнительное покрытие в `etl.call_detail_runs`, `core.call_details`; состояния complete/partial/failed, показатели total/covered/missing/mismatches. `Pipeline.run()` может завершить основной сбор после отдельно перехваченной ошибки дополнительного этапа. Успех основных вызовов не равен полноте детализации; `collect()` при проверке не запускать.
- Пульс `zarya-analysis/app.py`, `skorozvon()` читает `analytics.project_daily` и `analytics.refresh_status(status,last_success_at)`. `skorozvon_dashboard.py` использует `analytics.project_dashboard` с `refreshed_at`. Установить реальные определения витрин и охват обновления; максимум refreshed_at одной строки не доказывает свежесть всех проектов/дней.
- Выражения `coalesce(sum(...),0)` в отчёте могут показывать ноль для пустой выборки. Отдельно проверить строки и покрытие, прежде чем трактовать отображаемый ноль как отсутствие вызовов.

## Проверочные ситуации

| Наблюдение | Допустимый вывод и следующая проверка |
|---|---|
| Ночной запуск завершён сегодня, в его scope только directory | Справочники обновлены в пределах подтверждения; по звонкам требуется отдельный запуск/охват. |
| Сегодня нет событий, но есть успешная полная загрузка вчерашних суток | Сегодняшняя оперативная активность этим источником не покрыта; ноль за сегодня не установлен. |
| Последний вызов старый, успешное пустое окно свежее | Возможно отсутствие новых вызовов; проверить объём ответа, полноту и фильтры, не диагностировать остановку по max(started_at). |
| Mango вернул повторную полную страницу, запуск success | Возможное преждевременное завершение; total/полноту не подтверждать одним success. |
| Скорозвон received=500, inserted=0, updated=0, skipped=0 | Совместимо с идемпотентной повторной загрузкой 500 уже известных неизменённых записей. |
| Core свежий, витрина старая | Проблема отчётного слоя возможна; не обвинять сборщик и не запускать refresh без поручения. |
| Основной запуск success, детализация partial: 90 из 100 | Для основных вызовов и причин/таймингов разные границы; покрытие нужной детализации 90%, десять остаются неизвестными. |
| ChatApp success, у части каналов status_error | Свежий снимок получен с неизвестным состоянием этих каналов; не называть их отключёнными либо работоспособными. |
| Поля hold_duration нет в столбцах, в JSON оно null | Поле доступно, значение не заполнено в проверенном наборе; это не нулевая длительность. |
| В UI 1000 строк, сохранены только 200 raw записей | Можно описать образец raw; полную долю ошибок и полноту JSON не утверждать. |

Отчёт фиксирует, для какого показателя данных хватает и какое свидетельство отсутствует. Не обещать живую проверку, если просмотрены только код и датированные ориентиры.
