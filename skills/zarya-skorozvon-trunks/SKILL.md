# Заря: транки Скорозвона

## Источники и разрешения

Применяй также `zarya-crm-semantic-layer` для определения источников. Озеро и аналитические БД — только чтение: ограниченные SELECT в read-only транзакции, таймаут запроса, завершение rollback. Не менять учётку, сборщик, инфраструктуру или настройки оператора.

Доступы: сначала локальную инструкцию доступа проекта, затем только нужное существующее подключение без вывода секретов. Историческое название транка, регистрация и наличие доступа не подтверждают текущий маршрут или разрешение на переключение.

«Проверь» означает диагностику и рекомендации. Переключение допускается только в рамках текущего прямого поручения с определёнными проектами, пулом и ограничениями. Уже данное достаточное разрешение не запрашивать повторно. Не создавать и не возобновлять автоматизации без отдельного запроса.

## Диагностика

Для источников и метода полной выгрузки прочитай [references/collection.md](references/collection.md).

1. Зафиксируй момент среза и интервалы в Europe/Moscow. Получи текущие проекты, состояния, назначения, каталог транков и журнал операций. Различай физический транк, API ID, алиасы, номера и линии.
2. Уточни актуальное определение Севера/Юга, целевые проекты, разрешённый пул, исключённые неисправные транки и резерв. Прошлый состав, число рабочих транков и часы работы не переносить автоматически.
3. Проверь свежесть загрузки и покрытие. Если аналитика отстаёт, дополни разрешённым отчётным API с проверкой полноты. Неполную выборку обозначай частичной; не рассчитывай точный общий итог по ней.
4. Посчитай попытки, соединения, причины завершения и динамику по одинаковым временным окнам. Дозвон = сумма соединений / сумма попыток × 100%, по проверенной формуле текущего отчёта. При нуле попыток процент не определён. Не усредняй проценты проектов.
5. CPS считай по началам уникальных попыток за секунду, совместно по проектам одного физического транка. Не путай CPS, число параллельных каналов и средний темп. Локальный контрольный порог не называй лимитом оператора без подтверждения.
6. Фактический отдых резерва проверяй по всем доступным проектам, включая Юг, тестовые и выключенные, а не только по целевым. Отсутствие назначения в активных северных проектах само по себе не доказывает отдых.

Соединение не доказывает разговор с человеком. Регистрация не доказывает исправность исходящих. Отсутствие вызовов до начала работы не является отказом. Неустановленный транк в детализации не приписывать резерву либо рабочему транку по догадке.

## План и разрешённое выполнение

- Предложение должно перечислять конкретные проекты, текущие и будущие API ID, причину, исключения и ожидаемый состав. Учитывай ручные изменения, реальные попытки, совмещённые пики и отдых; не объявляй улучшение дозвона эффектом ротации без сопоставимого наблюдения.
- Перед записью перечитай назначения и проверь существующие автоматизации/журнал, чтобы не дублировать чужую операцию. Неизвестный или изменившийся пул требует проверки, а не применения старого плана.
- Сохрани локальный журнал без секретов: исходное назначение, целевое, время и результат каждого проекта. Меняй только разрешённую привязку штатным интерфейсом приложения/API. Паузные, завершённые, тестовые и чужие проекты не запускать и не перенастраивать за пределами поручения.
- После каждой операции проверь прикладной результат и повторно прочитай назначение. Таймаут после записи = неопределённый результат: не повторяй изменение вслепую; сверь живое состояние и журнал. При конфликте или неясном результате останови зависимые записи, сохрани выполненную часть. Не откатывай поверх ручных изменений автоматически.

## Результат

Компактно укажи срез МСК, покрытие/свежесть, рабочие и резервные транки, проекты и изменения. Дай попытки / соединения / процент, ошибки, пики и вывод за запрошенные окна. Разделяй рекомендацию, выполненную привязку и результат реальных звонков. При частичном выполнении перечисли подтверждённые и оставшиеся операции.
