# Отправка ТНБ

Навык описывает кампанию и контроль, а не предоставляет готовое подключение. Установка навыка сама по себе не разрешает отправки. Рабочий отправитель, источник доступов и отдельная очередь должны быть установлены локально; при их отсутствии не считать интеграцию готовой.

## Когда применять

- Запуск или продолжение согласованной кампании ТНБ.
- Вопросы «почему мало отправок», «сколько ожидают», «сколько доставлено и есть ли ответы».
- Добавление лидов за прошлые дни в пределах прямого поручения.
- Контроль единственного процесса и периодические отчёты.

Используй zarya-chatapp-campaigns для правил API и журналирования, zarya-crm-semantic-layer для интерпретации Озера. CRM строго только чтение; никаких изменений стадий, роботов, каналов или назначений.

## Согласованные условия кампании

Профиль, подтверждённый 4 ноября 2026 года:
- Макрорегион Север, 13 источников из локального sources.json.
- Отбор по дате перехода в ТНБ, независимо от создания лида. Перед отправкой текущая стадия всё ещё ТНБ.
- Основной сбор с 4 ноября; отдельным поручением добавлен исторический период 1–3 ноября. Границы и факт добавления хранятся в локальном аудите. Не переносить этот диапазон автоматически на новые кампании.
- MAX первым. WhatsApp только после подтверждённого отсутствия аккаунта MAX. Telegram не используется.
- Окно 09:00–21:00 МСК, проход каждые 15 минут, максимум одна отправка с каждой линии за проход.
- Только рабочие линии КЦ Севера, исключая КЦ УД; лицензия и состояние канала проверяются отдельно.
- Текст из согласованного message.txt: обращение получено, не удалось дозвониться, информация о законных вариантах снижения долговой нагрузки и приглашение на консультацию. Не менять предложение или ссылки без основания в поручении.
- Переход на время клиента обсуждался, но не был утверждён. Не считать вопрос о возможности изменением расписания. При отдельном поручении определять часовой пояс по проверенному городу/региону CRM и согласовать поведение для неизвестного пояса; не угадывать по телефонному коду.

Для новых кампаний повторно установить даты, регион, источники, текст, окно и лимиты. Текущие номера линий и счётчики не хранить в навыке.

## Отбор и объяснение очереди

1. В ограниченной READ ONLY транзакции проверить базу, карту статусов и временную зону; передавать явные границы МСК. Источник и регион являются текущими полями, если история их значений недоступна.
2. Считать отдельно события переходов, уникальные лиды, текущие ТНБ и уникальные валидные телефоны.
3. Нормализовать телефоны без отсечения произвольных значений до последних цифр. Учитывать несколько телефонов/лидов и дедупликацию по получателю.
4. Сопоставить с accepted, unknown, pending, исключениями и локальными отказами. Не возвращать уже отправленных и неизвестные попытки в pending.
5. При добавлении прошлого периода повторно проверить текущий ТНБ, источники, регион и отказы. Добавлять только отсутствующих получателей атомарно в отдельную очередь; существующие состояния не перезаписывать. CRM не менять.
6. Сохранить локальный аудит диапазона, количества лидов/телефонов, добавленных, повторов и исключений. Историческая дата сама по себе не исключает отдельно разрешённого получателя.

Для ответа «почему мало» показать: сколько переходило за период, сколько остаётся ТНБ, сколько ушло в другие стадии, сколько принято API и ожидает, сколько исключено. Текущая стадия сама по себе не доказывает стадию в момент более раннего прохода.

## Единственный отправитель и контроль

Рабочие имена: tnb_campaign.py --run; отдельный каталог кампании с queue.sqlite, STOP, events.jsonl и runner.lock. Не использовать старую очередь другой кампании как очередь ТНБ.

- Перед запуском проверить точный путь процесса, аргумент --run, число экземпляров, STOP и неизвестные попытки. Импорт помощника разрешён только после проверки отсутствия отправок и изменений очереди при импорте.
- Запускать только существующий утверждённый отправитель. На Windows использовать абсолютные пути к проверенному Python и скрипту, Start-Process -WindowStyle Hidden. Работающий процесс не дублировать.
- При STOP/unknown не перезапускать и не повторять сообщение. Сначала диагностика только чтением и уведомление; разрешение на восстановление другой кампании не распространяется на ТНБ.
- Записывать попытку до POST, сохранять серверный ID и chatId при подтверждённом принятии. Не использовать автоматический повтор POST при неизвестном результате.
- Ошибка проверки аккаунта не равна отсутствию аккаунта; отсутствие доставки не разрешает fallback. Suspended и ограничения не обходить другими линиями.
- Перед отправкой повторно проверить окно, текущую пригодность лида, доступность линии и STOP.
- Сохранить контрольный снимок процесса, состояний очереди и последних событий без телефонов и секретов.
- Пустая очередь не завершает непрерывный сбор новых ТНБ. Не удалять контроль только потому, что сегодня нет pending.

Проход каждые 15 минут не гарантирует отправку каждой линии в каждом проходе: отдельная выдержка 900 секунд от прошлой попытки может пропустить ближайший цикл. Проверять времена циклов и попыток, прежде чем называть это зависанием.

## Доставка и ответы

Использовать отдельный check_tnb.py либо проверенный GET-адаптер. Он не запускает отправитель, не меняет очередь, CRM и каналы. Не запускать два экземпляра проверки.

- Зафиксировать набор accepted и момент среза. Для каждого сообщения получить историю нужного chatId и сопоставить серверный messageId.
- Пройти пагинацию до момента индивидуальной отправки. Зафиксировать ошибки, повтор cursor, предел страниц и неполноту. Отсутствие ID в частичной истории не означает неотправку.
- Принято API не равно доставлено. delivered + viewed — доставлено; viewed — прочитано; sent — без подтверждения доставки. Эти значения использовать только после проверки контракта текущего адаптера.
- Входящие считать после фактического времени отправки, исключая системные события и журналы звонков. Дедупликация по line/channel/message ID.
- Отдельно считать сообщения и уникальных ответивших получателей. Приветствия и нейтральные ответы не считать интересом. Различать предварительный интерес, запись, отказ от услуги и отказ от дальнейших сообщений.
- Проценты считать от явно указанного количества accepted в том же проверенном срезе. Прочитанные входят в доставленные.
- Сохранять датированный JSON-снимок и локальные детали ответов. Публичные отчёты не содержат клиентских телефонов и секретов.

При действующем поручении отчёт каждые 2 часа: время МСК, MAX/WhatsApp/всего, accepted, delivered включая viewed, viewed, sent, ответы/ответившие, ошибки/полнота и прирост к предыдущему срезу. Отчётный график отдельный от 15-минутного контроля отправителя. Для периодичности использовать штатный инструмент автоматизаций и проверять существующие задания перед созданием.

## Границы публикации

В GitHub включать только методику и обезличенные примеры. Не включать queue.sqlite, журналы, отчёты с лидами, конфигурацию подключений, DPAPI-файлы, токены, частные пути и реальные тексты ответов. Наличие опубликованного навыка не доказывает доступность рабочего клиента или полноту данных Озера.
